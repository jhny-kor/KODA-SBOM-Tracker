# 구버전 리터럴 정책 자동이관 인수 — 2026-10-18

원본 4.0~4.7의 문자열 조건을 버전별 리터럴 의미로 자동이관합니다. 격리 Docker 프로젝트
`koda-native-verify-20261017`과 별도 **실제 4.7.1** 샘플 서버에서 원본 결과를 대조했습니다.
운영 데이터는 사용하지 않았습니다. 일반 KODA 실행에는 원본 서버가 필요하지 않습니다.

## 의미 보존

| 구분 | 구현 |
| --- | --- |
| PURL·CPE·SWID | 대소문자를 구분하는 substring 비교. `*`, `[`, `(?<=...)` 등을 정규식으로 해석하지 않음. 실제 식별자 null은 MATCHES·NO_MATCH 모두 위반 0개 |
| PURL 두 형태 | source API의 canonical 전체·좌표 PURL을 보존. 좌표 형태도 버전을 포함하며 qualifier·subpath만 제외. MATCHES는 각각의 원시 일치 개수, NO_MATCH는 모두 불일치일 때 1개 |
| 좌표 | 조건과 실제 값의 원본 trim/null 규칙, 조건이 정확히 `*`일 때만 wildcard, 필드별 NO_MATCH 후 AND |
| 버전별 차이 | 4.0·4.1의 좌표 버전은 리터럴. 4.2부터 비교 접두사를 처리. 4.0은 subject별 첫 결과 하나, 4.1부터 목록 개수 |
| ALL/ANY | 원본 ALL의 **원시 위반 개수 == 조건 개수**를 보존. ANY는 원시 개수 > 0. boolean AND로 바꾸지 않음 |
| 비문자열 혼합 | 등록 버전별 SEVERITY·CWE의 취약점별 개수, resolved-license UUID/그룹, VERSION·HASH 의미를 함께 보존 |
| XML 식별자 | CPE·SWID와 누락 optional 필드를 정규화해 JSON과 같은 리터럴/Java 정책 입력 제공 |

원본의 ALL에는 직관과 다른 결과가 있습니다. PURL 하나가 전체·좌표 형태에 모두 맞으면
원시 개수는 2이므로 단일 조건 ALL은 거짓입니다. 조건 두 개 중 PURL만 두 번 맞으면
원시 개수 2가 조건 수 2와 같아 ALL이 참이 될 수도 있습니다. 이를 원본과 다르게 고치지 않고
이관 조건의 count helper와 CEL 식에 보존했습니다. KODA 표시 결과는 정책·구성요소 단위이므로
원본 조건 행 개수와 별도로 비교합니다.

## 검증

- 백엔드 **563개 통과**. 실제 Java 21 회귀 검사와 새 리터럴·혼합 count·XML 검사를 포함합니다.
- 별도 원본 4.7.1에 실제 정책 39종·구성요소 5개를 생성했습니다.
- 원본 oracle에서 **조건 위반 34행 / 고유 정책·구성요소 33쌍**을 확인했습니다.
- Docker 통합 **52개**, 기존 주요 기능 회귀 **34개 통과**. 고유 정책·구성요소 **33쌍 전체**가 원본과 일치했습니다.
- 원본 4.7.1 서버를 정지하고 실제 Grype `0.109.1`과 `2026-10-10` DB(스키마 `6.1.10`)로
  **CVE 12건·리터럴 정책 결과**를 산출했습니다.
- Java 실행기를 사용할 수 없게 한 별도 분석에서도 리터럴 정책은 완료됐습니다.
- 새 리비전·과거 정책 스냅샷·원본 해시가 보존됐으며 worker 재기동 후 동일 결과를 재조회했습니다.
- 최종 이미지로 **8개 기본 서비스 전체 stop/up** 후 검사 **12개 통과**. 분석·정책·원본 해시 보존,
  원본 3개 서버 종료, 실행 이미지 모듈 해시, 새 실제 Grype 분석과 원본 33쌍 일치를 확인했습니다.
  실제 이미지에서 XML CPE·SWID 정책 입력과 5.x RE2 경로 분리, 구형 CWE wildcard의 null/빈 목록 구분도 확인했습니다.

버전 4.0·4.1·4.2·4.6의 차이는 태그별 원본 구현과 회귀 검사로 확인했으며 실제 API 대조는
4.7.1 기준입니다. 원본 버전 정보가 없거나 해당 버전에 등록되지 않은 조건, 원본 자체에서
null 입력으로 예외가 발생하는 구성은 정상 통과로 추정하지 않습니다.

## 재현과 증거

폐기 가능한 샘플 원본 전용입니다. 실행 중인 샘플 4.7.1 서버에 프로젝트·SBOM·정책을 만들며
KODA 정책을 일시 변경한 뒤 복구하고 샘플 원본을 정지합니다. 인증은 비공개 파일로 전달합니다.

```bash
python scripts/verify-literal-runtime.py \
  --env-file <격리된-테스트.env> \
  --source-auth-file <비공개-원본인증.json> \
  --fixture-file <샘플기록.json> \
  --output <결과.json>
```

주요 결과는 `output/literal-verification-20261018/report.json`과 `final-image-proof.json`입니다.
로컬 증거는 `output/literal-verification-20261018/`, 비공개 인증·샘플은
`runtime/literal-verification-20261018/`에 보관하고 Git에 포함하지 않았습니다.
지원 기능과 실제로 남은 차이는 [전체 비교 점검](native-parity-audit-ko.md)에 별도로 정리했습니다.
