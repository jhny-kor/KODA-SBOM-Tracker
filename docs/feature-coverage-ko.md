# KODA 자체 운영 기능 지원 범위

KODA가 직접 처리하는 기능과 운영자가 공급해야 하는 데이터, 이관·검증 경계를 구분합니다.
이 표의 **구현 확인**은 현재 코드에 해당 기능이 있다는 뜻입니다. 특정 운영 서버의 성공이나
모든 과거 제품과의 완전한 동등성을 뜻하지 않습니다. 실제 배포 확인은 아래 인수 기준을
따라 별도로 수행합니다.
**외부 플랫폼 제품 전체와 동등한 것은 아닙니다.** 추가 분석기·전용 전송기 등
[아직 미구현인 기능과 부분 지원](native-parity-audit-ko.md)을 별도로 확인하세요.
2026-10-18 격리 Docker의 실제 인수 결과와 환경 경계는 [검증 기록](verification-complete-20261018-ko.md)에 있습니다.

## 기능별 지원

| 영역 | KODA 처리 방식 | 현재 확인 범위 |
| --- | --- | --- |
| SBOM 관리 | 서비스·환경·릴리스·회차, CycloneDX JSON/XML, 원본 다운로드·보관·삭제 | 구현 확인. 과거 회차·분석 리비전과 원본을 분리해 보존 |
| 취약점 분석 | 실제 Grype 실행 파일과 반입한 Grype DB로 분석 | 구현 확인. DB 기준일·도구 버전·원본 결과를 기록하고 실패를 명시 |
| 지표 | 구성요소, 취약 구성요소, CVE·심각도, KEV, 정책 위반·경고·예외 | 구현 확인. 계산 정의와 데이터 기준일을 함께 비교해야 함 |
| 기본 정책 | 심각도·KEV·금지/미확인 라이선스·금지 구성요소 | 구현 확인. KEV 미공급은 비해당 통과가 아니라 데이터 부족 경고 |
| Collection 지표 | 직접 자식·최신 버전·태그·전체 하위 범위, 중첩 Collection, 집계 커버리지 | 최신 비보관 회차의 완료 분석을 사용. 미분석·재분석 대기·실패 뒤 이전 결과와 정책 미평가를 표시. 구성요소/취약점 발생 건수와 고유 취약점 ID를 구분 |
| 사내 취약점 DB | 내부/CVE ID, 영향 PURL·정확 버전·Maven/정식 SemVer 범위, 수정 버전, 초안·게시·철회·이력 | 게시 변경의 영향 회차 자동 재분석. 분석별 DB 리비전/해시 증거 보존. Grype와 함께 정책·VEX·회차/Collection 지표에 적용. 관리자·metadata.manage 권한 필요 |
| 고급 정책 | 표준 CEL, 구성요소·취약점·프로젝트 대상, 서비스·환경·릴리스와 동적 프로젝트 계층·태그·최신 버전 범위 | CWE·EPSS·달력 AGE·단위별 거리·SPDX·Java Matcher·구버전 리터럴 count helper 구현. Java 정규식은 실제 4.13.4와 대조. 표현식 오류·한도 초과는 정책 평가 실패로 기록 |
| 예외 | 정확한 정책·구성요소·선택적 취약점·회차·사유·만료일 또는 무기한 | 구현 확인. 다음 분석에서 적용하며 과거 판정은 변경하지 않음 |
| VEX·검토 | 작성과 독립 승인, 의견·결정 이력, CycloneDX VEX 가져오기/내보내기 | 구현 확인. 가져온 검토도 승인 전에는 탐지·정책 결과를 제외하지 않음 |
| 자동 재분석 | 모든 보관 전 회차 또는 최신 회차, 주기·범위, 데이터 갱신 후 후속 사이클 | 구현 확인. 용량·실행 중 작업·중단 복구를 대기열 상태로 관리 |
| 알림 | 결과 변경·분석 실패·검토 이벤트, 사용자별 읽음, 서명 Webhook·전송 재시도 | 구현 확인. 전용 이메일·메신저 전송기는 포함하지 않음 |
| 비교 | 회차·리비전 간 구성요소·CVE·정책 추가·해소·변경 | 구현 확인. 적용 정책·예외·VEX 변경도 결과 변화의 원인이 될 수 있음 |
| 인증·권한 | 로컬/LDAP, 승인, 역할 정책, 서비스 범위 API 토큰·CSRF·감사 CSV | 구현 확인. 실제 LDAP 서버와 조직별 권한은 대상 환경에서 검증 |
| 폐쇄망 운영 | 이미지·데이터 반입, 서명·manifest, 백업·복원·롤백 | 구현 확인. 실제 복원은 격리된 대상에서 별도 검증 |
| 기존 시스템 이관 | 원본 API/번들 → 사전 변환 검사 → 원자적 적용, 주기 동기화·재시도, 동적 카탈로그 | 실제 테스트 원본 서버에서 기본 정책 3개·발견 2개·검토 2개와 후속 고급 정책 9종·동적 계층 범위·주기 재시도·Grype 재분석 검증. 미지원 조건은 전체 적용 차단. 실제 운영 자료는 별도 확인 |
| 저장소 메타데이터 | npm·PyPI·Maven·NuGet·Go·Cargo 공식 저장소 수집·캐시·오프라인 반입 | Docker에서 6종 실수집과 CEL 반영 검증. Maven·Go 안정 릴리스 개수 및 단위 거리 지원. 색인·리비전·파일 시각은 구분 |

정책은 **준수 여부**를 판정합니다. 분석 작업의 **완료**와 정책의 **통과**는 별개이며,
정책 위반 자체가 외부 배포를 자동 차단하지는 않습니다. 외부 배포 차단이 필요하면
호출 측이 명시적으로 정책 상태와 데이터 완전성을 판정해야 합니다.

## 기존 시스템 이관의 확인 기준

| 대상 | 보존할 의미 | 동등성을 단정할 수 없는 경우 |
| --- | --- | --- |
| 프로젝트·버전 | 서비스·환경·릴리스·회차와 원본 식별자 대응 | 이름만 같고 실제 범위나 최신 버전 선택 기준이 다름 |
| 정책 | 대상·조건·연산자·결합 방식·범위·예외·라이선스 그룹 | 일부 조건을 생략했거나 필요한 메타데이터가 없음 |
| 취약점 | 구성요소 버전·CVE·분석기·데이터 기준일·검토 근거 | 다른 DB·분석기·기준일을 쓰면서 결과 건수만 비교함 |
| 검토·예외 | 사유·작성자·승인 근거·기한·정확한 적용 대상 | 예외를 전역 적용하거나 승인 전 내용을 유효 판정으로 간주함 |
| 지표 | 분모·중복 제거·위험 집계·억제 반영 방식 | 같은 지표 이름에 다른 계산식을 적용함 |

KODA 자체 기능이 있다는 사실과 기존 시스템의 모든 조건을 동등하게 변환했다는 주장은
다릅니다. 변환할 수 없는 조건은 보류하고, 확인되지 않은 메타데이터를 임의 값으로
채우지 않습니다. 원본 export와 백업은 검증이 끝날 때까지 유지합니다.

기존 SBOM 업로드·회차·분석·비교 API와 호환용 응답 계약은 별도로 검증합니다.
호환용 연결 상태·주소·동기화 결과가 있다는 사실을 KODA 자체 분석·정책 평가의
완료 근거로 사용하지 않습니다. 자체 분석 상태·정책 버전·지표를 함께 확인합니다.

## 배포 인수 기준

1. 기본 여덟 서비스가 새 기동과 재기동 뒤 모두 준비되고, 브라우저 로그인과 API 조회가 됩니다.
2. 알려진 취약 버전의 SBOM을 업로드해 실제 Grype DB로 CVE·수정 버전·정책 위반이 나오는지 확인합니다.
3. 정책·예외를 저장·재조회하고, 새 분석에만 적용되며 과거 리비전은 유지되는지 확인합니다.
4. VEX 작성·자기 승인 거부·독립 승인·다음 분석 반영을 검증하고 원본 탐지가 남는지 확인합니다.
5. 일정·데이터 변경 사이클, 대기열 부족·중단 복구, 알림·Webhook 실패와 재시도를 확인합니다.
6. 기존 자료 이관은 사전 확인 결과와 실제 이관 결과를 비교하고, 보류된 조건을 완료로 표시하지 않습니다.
7. 메타데이터가 필요한 정책은 실제 출처·수집 시각·실패 상태를 확인하며 데이터 부재를 통과로 간주하지 않습니다.
8. 격리된 복원 대상에서 서명·manifest·기록 수·원본 해시를 검증한 뒤 운영 전환합니다.
